## 一、NLA 系统架构总览

### 1.1 核心概念

NLA（Natural Language Autoencoder）是一个**双模型系统**，实现激活向量与自然语言之间的双向映射：

```
                     ┌──────────────────────┐
                     │    残差流激活向量      │
                     │   (3584-dim float32)  │
                     └──────┬───────┬───────┘
                            │       │
                     ┌──────┘       └──────┐
                     ▼                      ▼
              ┌────────────┐        ┌────────────┐
              │  AV (Actor) │        │ AR (Critic)│
              │  激活→文本   │        │  文本→激活   │
              └──────┬─────┘        └──────┬─────┘
                     │                      │
                     ▼                      ▼
              ┌────────────┐        ┌────────────┐
              │ 自然语言描述 │ ────▶  │ 重建激活向量 │
              └────────────┘  评分   └────────────┘
                              MSE/cos
```

**AV（Activation Verbaliser / Actor）**：一个微调过的 Qwen2.5-7B 模型，通过将激活向量注入到提示词中生成自然语言描述。训练目标是最小化 Critic 的重建误差（RL 奖励信号）。

**AR（Activation Reconstructor / Critic）**：一个截断的 K+1 层 Qwen2.5-7B 主干 + Linear(d,d) 重建头。输入自然语言描述，输出重建的激活向量。与原始向量的方向 MSE 作为重建保真度评分。

### 1.2 模型规格

```
基座模型：Qwen2.5-7B-Instruct
  - 总层数：28
  - d_model（隐藏维度）：3584
  - 词表大小：152064
  - 最大序列长度：32768
  - 精度：bfloat16（推理）
  - GPU 内存占用：约 14-16 GiB（基座模型），约 14 GiB（Critic）

NLA AV（Activation Verbaliser）：
  - 路径：/NAS/chennc/shared/models/kitft/nla-qwen2.5-7b-L20-av
  - 训练层：第 20 层
  - 注入缩放（injection_scale）：150.0
  - 嵌入缩放（embed_scale）：1.0（Qwen 架构不需要 √d 缩放）
  - 注入标记：㈎ (U+320E, token ID 149705)
  - 训练方式：RL（PPO/GRPO），奖励信号来自 Critic 的方向 MSE

NLA AR（Activation Reconstructor / Critic）：
  - 路径：/NAS/chennc/shared/models/kitft/nla-qwen2.5-7b-L20-ar
  - 层数：21（前 K+1=21 层截断版）
  - 输出头：Linear(3584, 3584, bias=False)
  - MSE 缩放（mse_scale）：59.87（√d_model = √3584）
  - 提取位置：tokens[-1]（最后一个 token）
  - 训练方式：监督学习，MSE 损失
```

### 1.3 nla_meta.yaml（sidecar 契约文件）

每个 NLA 检查点目录包含一个 `nla_meta.yaml` 文件，作为模型和代码之间的契约：

```yaml
kind: nla_model          # 或 nla_dataset
role: actor              # actor（AV）或 critic（AR）
d_model: 3584

extraction:
  injection_scale: 150.0   # AV 期望的注入 L2 范数（Actor 侧）
  mse_scale: 59.87         # Critic 的 MSE 缩放因子（Critic 侧）
  d_model: 3584

tokens:
  injection_char: "㈎"
  injection_token_id: 149705
  injection_left_neighbor_id: 271    # 注入标记左侧 token ID
  injection_right_neighbor_id: 994   # 注入标记右侧 token ID

prompt_templates:
  av: "Provide a detailed explanation of what information is encoded in this\
       \ representation vector, considering the context: <concept>㈎</concept>\n\
       \n<explanation>"
  ar: "The following is an explanation of a representation vector extracted\
       \ from a language model. Based on this description, reconstruct the\
       \ semantic content of the original vector.\n\nExplanation: {explanation}\n\
       \n<summary>"
```

**为何需要邻居匹配验证**：注入标记可能出现在多轮对话或粘贴文本中。仅查找 token ID 不够——必须验证注入标记两侧的邻居 token 与契约匹配，以确保注入到正确位置。

## 二、Actor（AV）注入机制详解

### 2.1 注入流程（单向量 → SGLang → 自然语言）

```
步骤 1：向量归一化
  raw_v [3584] → L2 归一化至 injection_scale(=150.0)
  v_scaled = raw_v / ||raw_v|| * 150.0

步骤 2：提示词嵌入
  prompt = "Provide a detailed explanation...<concept>㈎</concept>"
  → tokenize → input_ids [1, T]
  → embedding lookup → embeddings [1, T, 3584]
  → embed_scale 乘法（Qwen: 1.0）

步骤 3：注入位置定位
  扫描 input_ids，找到 token_id == 149705（㈎）
  验证左侧邻居 == 271，右侧邻居 == 994
  → 注入位置 p = 找到的索引

步骤 4：覆盖嵌入
  embeddings[0, p] = v_scaled

步骤 5：发送至 SGLang
  POST /generate
  Body: {
    "input_embeds": embeddings[0].tolist(),  # [T, 3584]
    "sampling_params": {
      "temperature": 0.0,
      "max_new_tokens": 200,
      "skip_special_tokens": false
    }
  }

步骤 6：解析输出
  SGLang 生成文本 →
  提取 <explanation>...</explanation> 标签内容
  如无标签 → WARNING + 返回原始文本前 200 字符
```

### 2.2 注入数学定义

设原始激活向量为 **v** ∈ ℝᵈ，其 L2 范数为 ||v||：

```
v_scaled = v / ||v|| × injection_scale
```

嵌入表查找得到 **E** ∈ ℝᵀˣᵈ，将注入位置 p 的嵌入替换：

```
E'[p] = v_scaled
E'[i] = E[i]  (i ≠ p)
```

SGLang 从 E' 开始自回归生成，第一个 token 的 logits 来自对 E' 的最后一个位置的 Transformer 前向传播。

### 2.3 注入失败症状

如果注入静默失败（标记不匹配、向量缩放错误）：

- **CJK 输出**：注入标记 ㈎ 自身的嵌入被 SGLang 作为正常文本处理，NLA AV 开始"联想"中文内容
- **"CJK char in English description"** ：NLA AV 描述的是一个 CJK 字符的外观/含义，而非语义内容
- **通用/无意义输出**：向量 OOD（例如未归一化至正确范数），AV 退化为训练先验

### 2.4 关键约束

- **必须禁用 Radix 缓存**（`--disable-radix-cache`）：Radix 缓存基于 token ID 进行键匹配。input_embeds 请求没有 token ID，不同嵌入序列会别名到同一缓存条目 → 静默错误。
- **injection_scale 不可随意更改**：150.0 是训练时的值。改变它 = 向量进入 OOD 区域 → 解码质量下降。
- **邻居验证是必须的**：代码中 `inject_at_marked_positions()` 函数在扫描到 ㈎ 位置后，会验证 p-1 和 p+1 的 token ID 与 sidecar 契约匹配。不匹配则崩溃报错，而非静默注入错误位置。

## 三、Critic（AR）评分机制详解

### 3.1 Critic 架构

```
输入文本（NLA AV 解码输出）
        │
        ▼
┌───────────────────────────┐
│ Tokenizer                  │  BOS + critic_template.format(explanation=text)
│ prompt: "The following...  │
│ <summary>"                 │
└───────────┬───────────────┘
            │ input_ids [1, T']
            ▼
┌───────────────────────────┐
│ 21 层截断版 Qwen2.5-7B     │  K=20 → K+1=21 layers
│ (前 21 层，不含 lm_head)    │
│ final LayerNorm → Identity │  替换为恒等映射
└───────────┬───────────────┘
            │ last_hidden_state[0, -1]  [3584]
            ▼
┌───────────────────────────┐
│ Linear(3584, 3584, bias=F)│  value_head (从 value_head.safetensors 加载)
└───────────┬───────────────┘
            │ pred [3584]
            ▼
    方向 MSE 计算
    与原始激活向量 gold [3584] 比较
```

### 3.2 MSE 计算公式

```
pred_n = pred / ||pred|| × mse_scale    # L2 归一化至 √d
gold_n = gold / ||gold|| × mse_scale    # 同上

MSE = mean((pred_n - gold_n)²)          # 逐元素均方误差
cos = pred_n · gold_n / (||pred_n|| × ||gold_n||)  # 余弦相似度
```

**MSE 与 cos 的等价关系**（当双方都归一化至相同 L2 范数时）：

```
MSE = 2(1 - cos) → 范围 [0, 4]

cos = 1.0  → MSE = 0.0   完美重建
cos = 0.9  → MSE = 0.2   良好解码（典型清洁位置）
cos = 0.5  → MSE = 1.0   中等
cos = 0.0  → MSE = 2.0   正交
cos = -1.0 → MSE = 4.0   反向（实践中从未出现）
```

### 3.3 mse_scale 的设计理由

选择 `mse_scale = √d_model = √3584 ≈ 59.87` 使 `.mean()` 产生与维度无关的 `2(1-cos)` 值：

- 两个向量都在 L2 范数 `s = √d` 下，逐元素 MSE = `2s²(1-cos)/d`
- 由于 `s²/d = d/d = 1`，所以 MSE = `2(1-cos)`
- 如果不乘以 √d，MSE 会是 `2(1-cos)/d ≈ 0.0005` —— 数量级太小，训练不稳定
- √d 的选择同时保持了训练时梯度的合理幅度

### 3.4 injection_scale vs mse_scale（不要混淆）

| 参数 | 值 | 用途 | 错误后果 |
|---|---|---|---|
| **injection_scale** | 150.0 | AV 注入时向量的 L2 范数 | 向量 OOD → CJK 输出 |
| **mse_scale** | 59.87 | Critic MSE 的缩放因子 | MSE 数值无意义（但仍单调） |

## 四、数据生成流水线（Parquet Generation Pipeline）

### 4.1 标准 parquet 生成

脚本：`scripts/make_qwen_layer20_demo_parquet.py`

```
┌─────────────────────────────────────────────────────────────┐
│                      Parquet 生成流程                        │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  1. 加载基座模型（Qwen2.5-7B-Instruct, bfloat16, cuda）      │
│                         │                                   │
│  2. 构造对话                                                │
│     messages = [                                            │
│       {"role": "system", "content": system_prompt},         │
│       {"role": "user", "content": user_prompt}              │
│     ]                                                       │
│                         │                                   │
│  3. 应用 chat_template + tokenize                           │
│     prompt_ids = tok.apply_chat_template(messages,          │
│         tokenize=True, add_generation_prompt=True)          │
│                         │                                   │
│  4. 基座模型贪婪生成（do_sample=False）                      │
│     full_ids = model.generate(                              │
│         prompt_ids, max_new_tokens=120,                     │
│         do_sample=False, pad_token_id=eos_token_id)         │
│     → 获得完整序列 [prompt_tokens + reply_tokens]            │
│                         │                                   │
│  5. 注册 forward hook 到目标层（layer 20）                   │
│     handle = layers[20].register_forward_hook(hook_fn)      │
│                         │                                   │
│  6. 对完整序列执行前向传播（use_cache=False）                 │
│     model(input_ids=full_ids, attention_mask=full_mask)     │
│     → hook 捕获 layer 20 的输出 [1, T, 3584]                │
│                         │                                   │
│  7. 提取回答部分的激活                                       │
│     reply_positions = range(prompt_len, full_len)           │
│     取前 max_rows=16 个位置                                  │
│     对每个位置 pos：                                         │
│       - n_raw_tokens: pos + 1                              │
│       - token_text: tok.decode([full_ids[pos]])             │
│       - detokenized_text: tok.decode(full_ids[:pos+1])      │
│       - activation_vector: hidden[pos] (float32 list)       │
│                         │                                   │
│  8. 写入 parquet + manifest JSON                             │
│                         │                                   │
└─────────────────────────────────────────────────────────────┘
```

**关键实现细节**：

1. **两次前向传播**：
   - 第一次：`model.generate()` —— 贪婪自回归生成回答
   - 第二次：`model(input_ids=full_ids, use_cache=False)` —— 对完整序列（提示词 + 回答）做一次 teacher-forcing 前向传播。`use_cache=False` 确保每层都对完整序列产生完整的隐藏状态输出。

2. **Hook 机制**：
   ```python
   def hook(_module, _inputs, output) -> None:
       nonlocal captured
       o = output[0] if isinstance(output, tuple) else output
       captured = o.detach().float().cpu()
   ```
   Hook 注册在指定的 TransformerBlock（`layers[layer_index]`）上。捕获的是该层的输出（残差流经过该 block 后的结果）。

3. **仅保存回答 token**：只提取 `range(prompt_len, full_len)` 中的前 `max_rows` 个位置。提示词处理阶段的激活不被保存。

4. **Parquet schema**：
   ```
   n_raw_tokens:           int64       # 包含当前 token 的总序列长度
   token_text:             string      # 当前 token 的文本（含特殊 token）
   detokenized_text_truncated: string  # 到此位置为止的解码文本
   activation_vector:      list<float32, 3584>  # 激活向量
   activation_layer:       int64       # 提取层号
   doc_id:                 string      # 文档标识（"qwen_demo_reply"）
   source:                 string      # 来源（"base_model_greedy_reply"）
   ```

### 4.2 位置分辨 parquet 生成

脚本：`scripts/make_position_resolved_parquet.py`

与标准生成的**关键区别**：

| 特性 | 标准生成 | 位置分辨生成 |
|---|---|---|
| 回答长度 | 80-120 token（默认） | **180 token（更长，保证中/晚期窗口有意义）** |
| 采样位置 | 前 16 个 token（顺序） | **早期(0-15)、中期(N/2±8)、晚期(N-16..N-1)** |
| 窗口列 | 无 | **window: "early"/"mid"/"late"** |
| 额外列 | 无 | **abs_position, window** |
| 生成温度 | 默认 | **temperature=0（贪婪解码）** |

**窗口定义算法**：
```python
early_start = prompt_len                        # 模式：回答第 0 个 token 起
mid_start = prompt_len + reply_len//2 - 8       # 模式：回答中点 ± 8
late_start = full_len - 16                       # 模式：倒数第 16 个 token 起
# 确保 late_start ≥ prompt_len
late_start = max(prompt_len, min(late_start, full_len - 1))
```

### 4.3 批量生成脚本

脚本：`scripts/exp_generate_parquets.py`

```
┌──────────────────────────────────────────────────────┐
│              批量 Parquet 生成流程                     │
├──────────────────────────────────────────────────────┤
│                                                      │
│  输入：docs/exp/plan_X.yaml                           │
│        │                                             │
│  解析 YAML：                                         │
│    plan_name = cfg["plan"]                           │
│    defaults  = cfg["defaults"]  # 公共参数             │
│    variants  = cfg["variants"]  # 变体列表             │
│        │                                             │
│  对每个变体：                                          │
│    system = variant.get("system", defaults["system"]) │
│    prompt = variant.get("prompt", defaults["prompt"]) │
│    output  = $NLA_TMP_ROOT/exp/{plan}/{name}.parquet │
│        │                                             │
│    subprocess.run([                                  │
│      python, make_qwen_layer20_demo_parquet.py,      │
│      --base-model $QWEN_BASE_MODEL,                  │
│      --output {output},                              │
│      --prompt "{prompt}",                            │
│      --system "{system}",                            │
│      --layer-index 20,                               │
│      --reply-tokens 120,                             │
│      --max-rows 16                                   │
│    ])                                                │
│        │                                             │
│  try/except: 捕获子进程错误，汇总失败数                │
│                                                      │
└──────────────────────────────────────────────────────┘
```

**设计决策**：使用 `subprocess.run()` 而非直接导入函数。原因：
1. `make_qwen_layer20_demo_parquet.py` 没有可复用的函数——所有逻辑在 `main()` 中
2. 子进程隔离：一个变体失败不会丢失先前的生成结果
3. 内存隔离：每个子进程独立加载和释放基座模型

## 五、推理流水线（Inference Pipeline）

### 5.1 SGLang 启动

脚本：`scripts/launch_qwen_nla_sglang.sh`

```bash
python -m sglang.launch_server \
    --model-path /NAS/chennc/shared/models/kitft/nla-qwen2.5-7b-L20-av \
    --port 30000 \
    --disable-radix-cache \           # 必须！input_embeds 与 radix 缓存不兼容
    --mem-fraction-static 0.75 \      # KV 缓存占 75% GPU 内存
    --attention-backend flashinfer \  # FlashInfer 作为注意力后端
    --sampling-backend flashinfer \   # FlashInfer 作为采样后端
    --trust-remote-code               # Qwen 需要
```

**GPU 内存占用（A40 46 GiB）**：
```
NLA AV 模型权重：约 14 GiB (bfloat16 × 7B 参数)
KV 缓存预留：约 34.5 GiB (0.75 × 46)
总占用：约 39-40 GiB
剩余：约 5-6 GiB（用于临时计算）
```

### 5.2 NLA 推理（解码）

脚本：`nla_inference.py` 的 CLI + `scripts/exp_run_inference.sh`

```
┌────────────────────────────────────────────────────────────┐
│                     NLA 推理流程                             │
├────────────────────────────────────────────────────────────┤
│                                                            │
│  1. 初始化 NLAClient                                       │
│     - 加载 tokenizer                                       │
│     - 解析 nla_meta.yaml → NLAConfig                       │
│     - 验证：注入标记 token ID 匹配、邻居 token ID 匹配       │
│     - 加载 embedding 表（~300 MB, bf16, CPU）               │
│                                                            │
│  2. 从 parquet 读取激活向量                                 │
│     batch = pf.iter_batches(batch_size=n,                  │
│              columns=["activation_vector"])                │
│     flat = batch.column("activation_vector")               │
│              .flatten().to_numpy()                         │
│     vecs = flat.reshape(n, 3584)  # [n, 3584]              │
│                                                            │
│  3. 对每个向量 v ∈ vecs[0..n-1]:                           │
│     a. normalize_activation(v, 150.0)                      │
│        → v_scaled[3584], ||v_scaled|| = 150.0              │
│     b. _build_embeds(v_scaled)                             │
│        → prompt tokenize → embed → scale → inject          │
│        → injected_embeds [T, 3584] on CPU                  │
│     c. _sglang_generate(injected_embeds)                   │
│        → orjson.dumps({"input_embeds": ..., ...})         │
│        → POST http://localhost:30000/generate              │
│        → SGLang 从注入嵌入开始自回归生成                    │
│        → 返回生成的文本                                     │
│     d. 提取 <explanation> 标签                             │
│        EXPLANATION_RE = re.compile(                        │
│            r"<explanation>\s*(.*?)\s*</explanation>",      │
│            re.DOTALL)                                      │
│        → 如无匹配 → WARNING + 返回 raw[:200]               │
│     e. 输出：─── [i]  ||v||=XXX.X ─── + 解释文本           │
│                                                            │
│  4. 重定向到 {variant}.decode.log                           │
│                                                            │
└────────────────────────────────────────────────────────────┘
```

### 5.3 SGLang 通信协议

**请求格式**（HTTP POST）：
```json
{
  "input_embeds": [[-4.25, 1.109, 1.406, ...], ...],  // [T, 3584] float32
  "sampling_params": {
    "temperature": 0.0,
    "max_new_tokens": 200,
    "skip_special_tokens": false
  }
}
```

使用 `orjson.OPT_SERIALIZE_NUMPY` 直接将 numpy 数组序列化，避免 `.tolist()` 产生 448K 个 Python float 对象的中间开销。

**响应格式**：
```json
{
  "text": "<explanation>\nStructured article format with formal explanation pattern...\n</explanation>"
}
```

**关键约束**：
- **不要同时发送 `input_ids`**：同时存在时 SGLang 可能使用 `input_ids` 做 logprob 记录，导致与 `input_embeds` 不对齐
- **嵌入必须是 `[T, d]` 形状，非批处理**（单样本推理时）
- **嵌入在 CPU 上（numpy 数组），SGLang 内部转移到 GPU**

## 六、评估流水线（Evaluation Pipeline）

### 6.1 标准定量评估

脚本：`scripts/exp_quantitative_eval.py`

```
┌──────────────────────────────────────────────────────────────┐
│                    定量评估流程                                │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  1. 加载 NLACritic                                           │
│     - 从 nla_meta.yaml 读取 mse_scale、critic_prompt_template │
│     - 加载截断的 21 层 backbone (AutoModelForCausalLM)         │
│     - 剥离 lm_head → nn.Identity()                           │
│     - 替换 final LayerNorm → nn.Identity()                   │
│     - 加载 value_head.safetensors → Linear(3584, 3584)       │
│     - backbone.to(cuda).eval(), value_head.to(cuda).eval()   │
│                                                              │
│  2. 遍历所有 plan_X 目录下 parquet + decode.log 对            │
│                                                              │
│  3. 对每对 (parquet, decode_log):                             │
│     a. 从 decode_log 提取解释文本                             │
│        blocks = re.split(r'^───\s*\[\d+\].*$', text)        │
│        跳过：空块、[NLAClient] 开头、[smoke] 开头、含 WARNING  │
│        → explanations = [block1, block2, ...]                │
│                                                              │
│     b. 从 parquet 加载激活向量                                 │
│        batch = pf.iter_batches(columns=["activation_vector"])│
│        → vecs [n, 3584]                                      │
│                                                              │
│     c. 对每个位置 i:                                          │
│        nm = ||vecs[i]||                                      │
│        mse, cos = critic.score(explanations[i], vecs[i])     │
│          注：critic.score() 流程见 §3.2                       │
│        → 记录 (plan, variant, position, norm, mse, cos)      │
│                                                              │
│  4. 聚合统计                                                   │
│     - 按 plan/variant 分组：mean/max/min/σ                    │
│     - 计划级别汇总                                             │
│     - Plan C 安全梯度专门分析                                  │
│                                                              │
│  5. 输出                                                      │
│     - quant_scores.csv：逐行原始评分                          │
│     - quant_report.md：Markdown 格式汇总报告                  │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

**decode_log 解析细节**：
```
日志格式：
─── [0]  ||v||=121.5 ─────────────────────
<explanation>
Structured article format...
</explanation>
─── [1]  ||v||=127.8 ─────────────────────
...

正则表达式：r'^───\s*\[\d+\].*$'
- 匹配以 ─── 开头、包含 [数字] 的行
- re.split() 按这些行分割文本
- 分割后的偶索引（0, 2, 4, ...）为解释文本
- 奇索引（1, 3, 5, ...）为数字匹配（被跳过）
- 空块、系统信息行、WARNING 行被过滤
```

### 6.2 位置分辨定量评估

脚本：`scripts/exp_position_resolved_eval.py`

与标准评估的**关键区别**：

| 特性 | 标准评估 | 位置分辨评估 |
|---|---|---|
| 数据源 | `exp/plan_*/` | `exp/position_resolved/` |
| 分组维度 | plan/variant | **condition/window** |
| 额外列 | position | **window, abs_position** |
| 报告重点 | 条件级 cos 均值 | **窗口级 cos 均值 + σ** |
| 特殊分析 | Plan C 安全梯度 | **C2/C5 结晶曲线、晚期方差分叉** |

## 七、实验编排框架

### 7.1 完整实验周期

一个完整的实验周期包含 5 个阶段：

```
阶段 1：YAML 配置设计
  ├── 编辑 docs/exp/plan_X.yaml
  ├── 定义 plan name, description
  ├── defaults: system, layer_index, reply_tokens, max_rows
  ├── inference: temperature, max_new_tokens, n_rows
  └── variants: [{name, prompt [, system]}, ...]

阶段 2：Parquet 生成（需要 GPU：基座模型 ~14-16 GiB）
  └── python scripts/exp_generate_parquets.py --config docs/exp/plan_X.yaml

阶段 3：SGLang 启动（需要 GPU：NLA AV ~28 GiB）
  └── bash scripts/launch_qwen_nla_sglang.sh &

阶段 4：NLA 推理（需要 SGLang 运行中）
  └── bash scripts/exp_run_inference.sh plan_X --temperature 0.0

阶段 5：定量评估（需要 GPU：Critic ~14 GiB，可与 SGLang 共享 GPU）
  └── python scripts/exp_quantitative_eval.py
  └── python scripts/exp_position_resolved_eval.py  # 如有位置分辨数据
```

### 7.2 GPU 调度策略

总共有 8 张 NVIDIA A40（46 GiB 每张），但部分 GPU 被其他用户占用。

| GPU | 用途 | 内存需求 |
|---|---|---|
| GPU 4/5/7 | 基座模型生成（阶段 2） | 14-16 GiB |
| GPU 5 | SGLang NLA AV（阶段 3-4） | 28-40 GiB |
| GPU 4/5/7 | Critic 评分（阶段 5） | 14 GiB |

**共存约束**：
- 阶段 2（基座模型）和阶段 3-4（NLA AV）不能在同一 GPU 上运行（互相 OOM）
- 阶段 3-4（SGLang）和阶段 5（Critic）可以在同一 GPU 上（总占用 ~40+14=54 GiB，超出 A40 的 46 GiB —— 不共存）
- 最佳策略：阶段 2 在 GPU 4/7，阶段 3-4 在 GPU 5，阶段 5 在 GPU 7（等待阶段 2 结束后释放）

## 八、位置分辨扩展架构

### 8.1 与标准生成的差异

标准生成仅采样回答的前 16 个 token，位置分辨生成采样三个跨度的窗口：

```
┌─────────────────────────────────────────────────────────┐
│  回答序列：[token_0, token_1, ..., token_N-2, token_N-1] │
│                                                         │
│  标准：   [■■■■■■■■■■■■■■■■] · · · · · · · · · · · ·   │
│           ↑ 前 16 个                                     │
│                                                         │
│  位置分辨：[■■■■■■■■■■■■■■■■] · · [■■■■■■■■■■■■■■■■] · · [■■■■■■■■■■■■■■■■]│
│           ↑ early (0-15)        ↑ mid (N/2 附近)      ↑ late (N-16..N-1)│
└─────────────────────────────────────────────────────────┘
```

### 8.2 额外的输出列

| 列 | 类型 | 说明 |
|---|---|---|
| `abs_position` | int64 | 在完整序列中的绝对位置 |
| `window` | string | "early" / "mid" / "late" |

### 8.3 生成参数差异

```
标准：--reply-tokens 80-120, temperature=default
位置分辨：--reply-tokens 180, temperature=0（贪婪解码）
```

原因：更长的回答确保中/晚期窗口能从有意义的位置采样。temperature=0 确保确定性，便于跨条件比较。

## 九、常见问题与调试

### 9.1 SGLang 启动失败

| 症状 | 原因 | 解决 |
|---|---|---|
| `FileNotFoundError: ninja` | flashinfer JIT 需要 ninja | `export PATH="/path/to/conda/env/bin:$PATH"` |
| `torch.OutOfMemoryError` | GPU 内存不足 | 换空闲 GPU，或降低 `--mem-fraction-static` |
| `ModuleNotFoundError: sglang` | 未激活正确 conda 环境 | `conda activate nla` 或使用完整 Python 路径 |

### 9.2 NLA 解码质量差

| 症状 | 可能原因 |
|---|---|
| 所有输出为 CJK 字符 | 注入失败：㈎ 的嵌入未被覆盖，AV 将其视为文本 |
| 输出描述 CJK 字符的外观 | 同上——注入标记泄漏为正常文本 |
| 通用/模糊/无意义输出 | 向量 OOD（未归一化至正确 injection_scale） |
| cos 异常低（< 0.7） | 向量来自训练分布外的层或位置 |
| WARNING: no \<explanation\> tags | 生成被截断（增大 max_new_tokens）或模型漂移 |

### 9.3 Parquet 生成失败

| 症状 | 原因 |
|---|---|
| `torch.OutOfMemoryError` | GPU 被其他进程占用或模型太大 |
| 基座模型拒绝回答（无 token 生成） | 提示词过于危险，Qwen 安全训练完全阻止 |
| 生成的回答太短（< 16 个 token） | 增大 `--reply-tokens` 或更换提示词 |

### 9.4 pyarrow 列名注意事项

pyarrow 的 list 类型内部子字段名为 `element`，所以 `pf.schema.names` 在某些版本中显示 `element` 而非顶层的 `activation_vector`。但通过 `columns=['activation_vector']` 读取是正确的。这是 pyarrow 的展示行为，不影响数据读写。
